# 교류 기록(합방) 실데이터 설계

작성일: 2026-08-16

## 1. 목표

그래프의 `interactions`(지금은 빈 배열)를 실제 합방/합동 커버 기록으로 채운다.
음악 탭과 마찬가지로 **새 합방이 생기면 자동으로 반영**되어야 한다.

## 2. 실측으로 검증한 사실

설계 전에 Worker에 임시 진단 코드를 넣어 실제 Holodex 응답을 확인했다 (구현 후 원복함).

### 2.1 `mentions`는 실재하고, 필터링이 핵심이다

`include=mentions`로 영상에 태그된 다른 채널을 받을 수 있다. 그런데 **org 전체
최근 영상에서 "우리 멤버 2명 이상이 mentions에 걸리는 영상"만 걸렀더니 10건 중
10건 전부 가짜였다** — 전부 노엘/마린/페코라 등을 언급한 **切り抜き(팬 클립) 채널**
영상이었다. 실제로 그 둘이 같이 나온 방송이 아니었다.

```
"白銀ノエル家の断捨離配信で...宝鐘マリン【ホロライブ切り抜き】"
업로더: "ホロライブ速報【切り抜きch】"  ← 노엘도 마린도 아님
```

### 2.2 해결책: `type=stream` 필터

`/videos?org=Hololive&status=past&type=stream&include=mentions`로 다시 조회하니
**8개 샘플 전부 `uploaderIsTracked: true`**로 바뀌었다. 클립 채널은 Holodex에서
`type=clip`(또는 별도 타입)으로 분류되기 때문에, `type=stream`(실제 방송 VOD)만
보면 자동으로 걸러진다. 7명이 참여한 합동 이벤트(あざとい王選手権: 라미·폴카·
쵸코·코요리·라플라스·아즈키·노엘)도 정확히 잡혔다.

→ **`uploaderIsTracked` 같은 별도 검증 로직이 필요 없다.** `type=stream`이면 충분.

### 2.3 실시간 합방은 `/live`로, 과거는 `/videos`로

- `/live?org=Hololive&include=mentions` — 기본값이 `status:[live,upcoming]`,
  `type:stream`이라 지금 방송 중/예정인 합방을 mentions와 함께 한 번에 받는다.
  6인 3D 콜라보까지 노이즈 없이 확인됨.
- `/live?status=past`는 **API가 거부한다** ("Should not use v2/live endpoint to
  query for 'past' videos"). 과거 기록은 `/videos?status=past&type=stream`으로
  받아야 한다.

### 2.4 39명 순회 조회가 필요 없어졌다

애초에 이 설계를 시작한 이유가 "org 전체로 보면 우리 멤버가 업로더인 게 드물어서
39명 개별 조회가 필요하다"였는데, `type=stream` 필터 하나로 org 전체 조회의
정확도가 확 올라가면서 **개별 채널 조회 없이 org 단위 호출 2개(`/live`,
`/videos&status=past`)로 충분**해졌다. Cron에서 39번 돌 필요가 없다.

## 3. 파이프라인

곡 아카이브(v0.2.3)와 동일한 패턴 — 요청 시점에 diff 확인 후 새 게 있을 때만
KV에 쓴다 — 을 그대로 재사용한다. 다만 사용자 요청으로 **Cron도 추가로 넣는다**:
요청 시점 폴링만으로는 트래픽이 없는 시간에 합방을 놓칠 수 있어서, Cron이
안전망 역할을 한다. 이제 org 단위 호출 2개뿐이라 Cron 비용 부담도 거의 없다.

```
[매 요청(60초 캐시)]              [Cron: 2시간마다, JST 08~22시]
  /live?include=mentions              (동일 로직)
  /videos?status=past&type=stream          │
  /videos?topic=Music_Cover...&include=mentions
        │                                  │
        └──────────► 참가자 ≥2 추출 ◄──────┘
                         │
                  KV(interactions-archive-v1)
                  기존 것과 id 대조, 새 것만 추가
                  (MUSIC_ARCHIVE 바인딩 재사용, 키만 다르게 — KV 새로 안 만듦)
```

### 스키마 (그래프 코드는 수정 불필요)

```jsonc
{
  "id": "yt:...",
  "type": "collab",          // Music_Cover/Original_Song 토픽이면 "cover"
  "participants": ["su", "vivi"],   // 3명 이상도 그대로 배열에
  "count": 1,
  "lastDate": "2026-08-15"
}
```

`NetworkGraph.jsx`의 감쇠 로직(`BASE_SCORE(20) ÷ 참가자 수`, 반감기 90일)이
이미 N명 참가를 위해 설계돼 있어서 그대로 재사용한다. 7명 이벤트가 들어오면
21개 쌍에 각각 20÷7≈2.86씩 기여 → 그래프에서 느슨한 클러스터로 자연스럽게 뭉침.

### 4.1 툴팁: N명 합동 이벤트 표시

지금 툴팁은 1:1 랭킹만 보여준다. `participants.length > 2`인 이벤트는 별도
섹션("최근 합동 이벤트")으로 추가해, "7명 합동 이벤트 참여" 같은 사실이
드러나게 한다.

### 4.2 그래프: 2명 합방 — 물리적으로 서로 당김 (수정: 실제 링크)

**최초안(표시만 토글)에서 수정.** 사용자 요청: "합방 중일 땐 물리적으로
연결되면 좋겠다." 재검토한 결과, d3는 시뮬레이션을 통째로 다시 만들지 않고도
`nodes`/`links` 배열에 항목을 추가·제거하고 `simulation.alpha(0.3).restart()`로
그 부분만 재가열할 수 있다 — **카메라(줌/팬 transform)는 완전히 별개 상태라
전혀 안 건드린다.** 처음에 걱정했던 "폴링마다 카메라가 리셋된다"는 문제는
SVG를 통째로 지우고 다시 그리는 **완전 재빌드**에서만 생기는 것이지,
d3의 일반적인 update pattern(`enter`/`update`/`exit`)으로 노드·링크를
증분 추가하는 것과는 무관하다.

그래서 `liveCollabs`가 바뀔 때(60초 폴링), 실제로:

1. 참가자 2명 사이에 **짧고 강한 링크**(거리 40~60px, 강도 0.8~1 —
   평소 감쇠 링크보다 훨씬 세게)를 `links` 배열에 추가
2. 색은 빨강, LIVE 링과 같은 톤
3. `force('link').links(links)`, `simulation.alpha(0.3).restart()`로
   국소 재가열 → 두 노드가 실제로 서로 끌려 붙음
4. 합방이 끝나면 이 링크를 배열에서 제거하고 다시 살짝 재가열 → 평소
   감쇠 거리로 자연스럽게 벌어짐 (이미 아카이브에 기록된 회색 교류선은
   그대로 남아 조금 더 두꺼워져 있음 — "가까워졌다"는 느낌)

메인 effect([members, interactions]에 종속, 거의 안 바뀜)는 그대로 두고,
`liveCollabs` 전용 별도 effect가 이 증분 갱신을 담당한다. LIVE 배지처럼
`updateLiveLinksRef` 같은 ref로 노출.

### 4.3 그래프: 3인 이상 합방 — 임시 주제 허브 (수정: 진짜 물리 노드)

**최초안(무게중심 오버레이)에서 수정.** 같은 이유로 오버레이 대신
**진짜 임시 노드**로 만든다.

1. `liveCollabs` 그룹마다 `{ id: 'hub:videoId', isHub: true, topic }`
   임시 노드를 `nodes` 배열에 추가
2. 참가자 전원 → 허브로 짧고 강한 링크 추가 (2명 합방과 같은 강도)
3. 화면엔 참고 이미지처럼 캡슐 모양 + 주제 텍스트로 그린다. **진짜 노드라서
   드래그도 된다** (오버레이 안이었다면 못 했을 것 — 오히려 이득)
4. `nodeSel`을 `.data(nodes, d => d.id).join(enter, update, exit)`로 다시
   바인딩 — 허브는 enter, 사라질 땐 exit에서 `.remove()`
5. 합방이 끝나면 허브 노드와 스포크 링크를 배열에서 제거 → exit 처리로
   자연스럽게 사라지고, 나머지는 원래 감쇠 거리로 재배치

**주제 텍스트 추출**: 완벽한 자연어 처리는 안 쓴다(폴링마다 비용 발생).
대신 각 참가자 방송 제목에서 `【...】`/`[...]` 안의 텍스트를 뽑아, 라이브 중인
그룹 사이에 **공통으로 걸려 있는 태그**가 있으면 그걸 주제로 쓰고, 없으면
"합동 방송"으로 표시하는 휴리스틱을 쓴다 (사용자 확인 완료). 정확도는
완벽하지 않음을 미리 밝혀둔다.

**동시에 여러 그룹이 라이브인 경우**: `liveCollabs`를 평평한 쌍 목록이 아니라
그룹 단위 배열로 설계해야 한다.

```jsonc
"liveCollabs": [
  { "videoId": "...", "topic": "마인크래프트 여름 서버", "participants": ["a","b","c","d"] },
  { "videoId": "...", "topic": null, "participants": ["e","f"] }
]
```

### 4.4 그래프: 교류선 클릭 → 합방 목록 팝업

지금은 쌍별로 감쇠 적용된 "점수"만 계산하고 개별 합방 기록은 버린다.
클릭했을 때 최신순 목록을 보여주려면, `buildPairStats`가 점수뿐 아니라
`Map<pairKey, event[]>`(제목·날짜·URL 원본 리스트)도 같이 만들어야 한다.
UI는 `MemberTooltip`과 같은 패턴(위치 추적, 화면 밖 보정 재사용)으로 만들되
내용만 "합방 목록"으로 다르게 채운다.

### 4.5 알림 피드: 예정 탭 주제별 묶기

4.3의 주제 추출 로직을 예정(upcoming) 알림에도 적용해, 같은 주제 태그를
공유하는 카드들을 그룹으로 묶는다. `NotificationSidebar`/`NotificationCard`에
그룹 헤더 + 접기/펼치기 UI가 추가로 필요하다.

### 4.6 교류선 임곗값 필터

노드 클릭 시 뜨는 "교류 멤버" 목록과, 그래프에 그려지는 선 자체 모두
합방 횟수가 일정 개수(예: 2회) 미만이면 숨긴다. 정확한 임곗값은 실데이터가
들어온 뒤 분포를 보고 정하는 게 나을 것 같다 — 너무 낮으면 노이즈,
너무 높으면 그래프가 휑해 보일 수 있다.

### 4.7 최소 거리 & 노드 분산

- 최소 거리: `distanceScale`의 range 하한(현재 90)을 유지하되, 클릭하기
  충분한 여유(노드 반지름 24 기준 테두리 간 42px)가 되는지 실측 확인.
- 노드 분산: `forceManyBody` 반발력을 강화하고(-260 → 더 음수),
  `forceX`/`forceY`의 중앙 쏠림 강도(0.03)를 낮추거나 컨테이너 크기에
  비례하도록 조정한다. 39개 노드 기준으로 캔버스 여백을 더 쓰도록 튜닝.

## 5. 애매했던 두 가지 — 답변

### Q1. 합방인데 일부만 방송을 켜는 경우, 참가자를 어떻게 판단하나?

**문제가 되지 않는다.** 판단 신호가 "동시에 여러 명이 live 상태"가 아니라
Holodex의 `mentions`(영상 하나에 다른 채널이 태그됐는가)이기 때문이다.
한 명만 방송을 켜고 나머지를 mentions에 태그해도, 그 영상 하나에서
전체 참가자를 뽑아낼 수 있다. "지금 합방 중" 판정 조건도 "영상이
`status=live`이고 mentions에 추적 멤버가 2명 이상"이지, 전원이 동시에
live 상태여야 하는 게 아니다.

### Q2. 같은 시간대 같은 인기 게임인데 합방이 아닌 경우는?

구조적으로 이미 회피된다. `mentions`은 "같은 게임을 한다"가 아니라
"이 영상이 다른 채널을 실제로 언급/태그했다"는 신호라서, 우연히 같은
인기 게임을 각자 따로 하는 경우는 서로를 mentions에 걸 이유가 없다.
2.1~2.2절 실측에서도 이런 유형의 오탐은 한 건도 나오지 않았다. 다만
Holodex 자체 태깅이 완벽하다는 보장은 없어서 8절 리스크에 남겨둔다.

`src/data/memberInteractions.json`에 저장, Worker가 KV 부트스트랩 시드로 사용.

## 8. 남은 리스크

- 개인 프로젝트 트래픽 규모에서 Cron(2시간 간격)도 완벽한 커버리지는 아니다 —
  같은 2시간 안에 org 전체에서 50건 넘는 과거 영상이 쏟아지면 그 사이 항목은
  누락될 수 있다. 실사용 규모에서는 거의 발생하지 않을 것으로 본다.
- `mentions`는 영상 설명/제목 기반 태깅이라 100% 정확하다는 보장은 없다
  (Holodex 자체의 태깅 정확도에 의존, Q1/Q2 참고).
- 주제 추출(4.3, 4.5)은 제목 태그 기반 휴리스틱이라 완벽하지 않다. 태그가
  없거나 서로 다르면 "합동 방송"으로 뭉뚱그려진다.
- 라이브 링크/허브가 매 폴링마다 추가·제거되며 `simulation.alpha()`로 국소
  재가열되는데, 이 강도를 잘못 잡으면(너무 세면) 합방 시작·종료 시점마다
  주변 노드들이 눈에 띄게 들썩일 수 있다. 실측하며 값 조정 필요.

## 9. 구현 순서 제안

범위가 커서 한 번에 다 만들기보다 단계별로 나누는 걸 추천한다.

1. **데이터 파이프라인** (2·3·6절) — 이게 없으면 나머지는 다 무의미하다.
2. **거저 얻는 것들** — 1·2번 항목은 파이프라인만 연결되면 자동으로 나옴.
   3·4·5·6번(임곗값, 최소거리, 2인 강조선, 노드 분산)은 기존 패턴 재사용이라
   빠르게 갈 수 있다.
3. **교류선 클릭 팝업** (7번) — 중간 난이도, 독립적으로 검증 가능.
4. **3인+ 허브, 예정 탭 그룹** (8·9번) — 가장 복잡하고 서로 의존(주제 추출
   로직 공유)하니 마지막에 같이.

이 순서로 가면 2단계까지만 해도 "실제 합방 데이터가 그래프에 살아있다"는
핵심은 이미 보여줄 수 있다.
